Components

Custom elements

Four components build their own DOM from data: icons, charts, code and texture fields. Each has an element that renders the same markup inside itself and lets the same Fire module draw it, so the two forms look and behave alike.

Element or markup

Load fire/elements.js (or import fire-design/elements) to register fd-icon, fd-chart, fd-code and fd-texture. It shares Fire's modules with fire/fire.js, so a page loads each module once.

Use the element

Inside Lit, React, Next.js or Vue, where a framework owns the DOM: an <i data-icon> that replaces itself, or a chart that rewrites its children, fights the framework's rendering. Pass data as a property (.data for charts, .code for code) and the element redraws when it changes.

Use the markup

On plain pages, in templates and in server-rendered HTML: the markup needs no element registry, reads its data from a <script type="application/json"> and is drawn by fire/fire.js like every other component.

  • Every attribute of an element is the markup form's data-* attribute without the prefix: data-height is height. The exceptions are names HTML already uses: language (for data-lang), marks (data-style), animated (data-animate), and type, which also names the chart (sparkline, donut, heatgrid).
  • Each element is its component's root: it carries the root class (fd-icon, fd-chart, fd-codeblock, fd-ascii…) and the markup form's data-* attributes, and holds the component's internals. Every Fire rule applies to it, direct-child rules such as .fd-btn > .fd-icon included. Classes you add are kept, and the element puts its own class back if a framework replaces class.
  • On this page the element sits on the left and its markup twin on the right; the test suite checks, in Chromium, Firefox and WebKit, that both have the same classes, attributes and internals and render to the same pixels.

fd-icon

icon names the icon and size picks 12, 14, 16, 20, 24 or 32. The icon is decorative: name the control that holds it. Inside a component it takes the component's icon rules, as the SVG does.

fd-chart

type picks the chart: line, area, bar, stacked, sparkline, donut or heatgrid. The data is the JSON the markup form carries; on a plain page it can go in the data attribute.

  • The element fires the chart's own events, which bubble from inside it: fd:hover and fd:select with the point, fd:change when a legend item toggles a series.
  • A cartesian chart keeps a custom yFormat function given in .data; donuts and heat grids are drawn from their JSON, so their formats are names.

fd-code

Give the text in code and the language in language. lines, highlight, collapse and wrap are the code block's own options; filename adds the header and copy the copy button.

  • The text is set as text, never parsed as HTML. Changing it renders the block afresh, so Fire never rewrites a text node your framework owns.

fd-texture

pattern picks the field; the field fills its nearest positioned ancestor, or flows at the field height with inline. The element is the field: it takes the markup form's class and attributes, and the module draws, sizes, colours and animates its canvas, and stops when it leaves the page.

  • Because the element is the field, its container layers it as it layers the markup form: above the container's background, below its content. Leave the element's class alone; style the container instead.

In a framework

Import the elements once, in client code, then bind data as a property. Fire's events have a colon in their names: Lit binds them as @fd:select; React needs a listener on a ref.
