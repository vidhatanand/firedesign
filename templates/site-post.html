How we cut the median scrape to 842 ms

In August a scrape took 1,310 ms at the median. Three changes took it to 842 ms: browsers that wait warm, a smaller snapshot of the page, and one fewer network hop.

  • JWJonas WeberStaff engineer, crawl infrastructure
Nov 4, 2026 8 min read

A scrape is one request to /scrape: Ember opens the page in a browser, waits for it to settle, and returns Markdown, HTML or JSON. For an agent that reads ten pages before it answers, the wait for each page is most of the wait for the answer.

Between August 3 and October 26 the median scrape went from 1,310 ms to 842 ms. The 95th percentile went from 4.8 s to 3.1 s. Nothing about the price changed: a scrape is still 1 credit.

Where the time went

We traced 200,000 scrapes in the first week of August and split each one into four stages. Starting a browser was the largest piece that did no useful work.

StageAugustOctober
Wait in the queue120 ms110 ms
Start a browser340 ms35 ms
Fetch and render610 ms520 ms
Snapshot and convert240 ms177 ms
Median scrape1,310 ms842 ms

Browsers that wait warm

Each region now keeps a pool of browsers started and idle, sized from the last hour of traffic. A request takes one that is ready; a new one starts behind it. The pool costs us memory, not you credits.

Starting a browser fell from 340 ms to 35 ms at the median, the time it takes to hand over one that is already running.

A smaller snapshot

To turn a page into Markdown we used to copy the whole DOM out of the browser, styles included, and convert it outside. Now the browser drops scripts, styles and hidden nodes before the copy, so there is less to move and less to parse. Snapshot and convert fell from 240 ms to 177 ms.

One fewer hop

A request used to pass through a proxy router before it reached the browser's region. The router now runs inside each region, beside the pool, so the page is fetched one hop closer. Fetch and render fell from 610 ms to 520 ms; most of the rest is the site itself.

What it changes for you

Nothing to switch on. Every plan gets the faster path, and a scrape that fails still costs nothing. If you set a timeout to cover the old median, you can lower it: 15 seconds covers 99.9% of scrapes today.
