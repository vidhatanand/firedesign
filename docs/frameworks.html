Start

Frameworks and checks

Fire works in plain pages, Lit, React and Next.js, and Vue. Start from a starter, follow a short list of rules, and let the checks prove the result. This page also covers how to find the right part, the package's entries and every command.

Start from a starter

Fire ships three wired apps. Each shows Ember's shell and three screens (overview, logs and settings), with the phone tab bar and page transitions, and each renders the same as Fire's own templates in three browser engines. Copy one folder and you have an app.

FrameworkStarterPackage entry
Lit (the default for a new app)starters/lit-vitefire-design/elements
React and Next.jsstarters/nextfire-design/react
Vuestarters/vue-vitefire-design/vue

Make it yours

  • Copy the starter folder out of the Fire repository.
  • Its package.json already depends on the tagged release below, locked in package-lock.json, so npm ci gives you the same Fire anywhere.
  • Run npm install, then npm run dev.
  • Choose your look by editing the theme record (Lit: theme.json; Vue: look.json; Next.js: set FIRE_LOOK). The starter turns it into a stylesheet before every run.
  • Delete the check script. It compares against templates that only exist in Fire's repository. Keep lint:markup and lint:css: both run in your project.
  • Each starter has data-fd-surface="app" on <html>, and its overview and logs screens open their loading, empty and error views from ?state=. Page transitions are on: Lit and Vue call transition(), and Next.js wraps each screen in React's <ViewTransition> (see Page transitions).
  • The Lit starter has a router of its own, with no dependency: a route table with parameters (/logs/:id), guards, a not-found page from Fire's 404 template, a base path, and each screen in its own chunk, loaded on the first visit or when a link to it is hovered. After each new screen it sets the title, moves focus to the heading and restores the scroll position on Back. Its first load fell from 221.6 kB of JavaScript (gzip, one script) to 196.5 kB in five files, of which the shared Lit and Fire chunks keep their names from one deploy to the next, and npm run check holds it to size budgets set in package.json. Most of what is left is Fire's behaviour chunk. The starter's README says what a product replaces and what its host must do.
package.json
"dependencies": {
  "fire-design": "github:vidhatanand/firedesign#v0.14.0"
}

Pin the tag

A tag names one release. Move to a new release by changing the tag, never by pointing at a branch.

The markup is the same in every framework. The packages and elements remove the few places where a framework and Fire would fight over the DOM.

Rules to remember

The full list, with a rule id each, is spec/EXPORT.md. These are the ones that break a screen when forgotten.

TopicRule
Presence attributesIn JSX write data-block="", never bare data-block, which renders "true". In Lit and Vue the bare form is fine (A7).
BooleansIn JSX write hidden, disabled and open with no value. hidden="" is dropped (A3).
JSON dataRow templates and chart data are <template> and <script type="application/json"> elements. Fill them with innerHTML or dangerouslySetInnerHTML through jsonForScript, which escapes < (M1, M2).
IconsNever <i data-icon> in framework code. Fire replaces it, and the framework then crashes on it. Write <fd-icon icon="search"> or the static SVG (I1, I2).
EventsListen for fd:select, fd:change and the rest on an element: @fd:select in Lit and Vue, useFireEvent in React. Next.js does not compile onfd:select (V1, V2).
InitFire runs once at load. Call init(root) after you render new markup: useFire(ref) in React, v-fire in Vue, updated() in Lit. Never before hydration (L1, L5).
Fire owns what it writesAfter init, never bind aria-expanded, data-state, role, id or the children of a chart, secret or code block to state. Change them through Fire's API, or change the element's key (O1, O2).
FieldsDo not control a field that Fire writes (search, number, slider, OTP, combobox). Use defaultValue and read fd:change (F7, O3).
No styleNo style attribute, prop or v-show. Custom properties go in data-fd-vars (A14, A17).
Server renderingRender plain Fire markup on the server. Load Fire in the browser after hydration. Put suppressHydrationWarning on <html> and on elements that carry data-fd-vars (N1, N3, N4).
Strict CSPFire works with script-src 'self'; style-src 'self'. The Vite dev server needs 'unsafe-inline' for styles. A production build does not (P1, P2).
The CSS targetSet build.cssTarget: ['chrome123', 'edge123', 'firefox120', 'safari17.5'] in vite.config. Vite's default target lowers light-dark(), and a forced color-scheme stops working (P5).
TypeScript
// vite.config.ts
export default defineConfig({
  build: { cssTarget: ['chrome123', 'edge123', 'firefox120', 'safari17.5'] },
});

The skill, and proposals as issues

skills/fire is an agent skill. It starts every screen from a reference screen, chosen by what the person is doing, then picks the parts, runs the checks, and files what Fire lacks as an issue. Link or copy the folder into the agent's skills folder once.

skills/fire/SKILL.mdThe order of work: find Fire, choose the reference screen, choose the parts, build by the rules, check, propose.
skills/fire/screens.mdEvery reference screen: its job, when to use it, what to use instead, its states, its file and its picture. Generated from the template cards. An agent reads it whole and chooses by meaning.
skills/fire/parts.mdOne line for every component, pattern, layout, website section and module, by family. Generated from the index.
node skills/fire/where.mjsPrints the project's Fire, the skill's Fire and the folder to read from. The reference screens, these docs pages and the pictures are in the package from 0.13.0.
npx fire propose new <slug> --kind componentWrites docs/fire/proposals/<slug>.md: what was being built, what was searched, and the component (card, markup, CSS). Kinds: component, variant, token, pattern, bug, accessibility.

npx fire propose send <file>Files the issue on Fire's repository with gh and writes its link into the file. --dry-run shows what it would post. An agent files one when the project's instructions allow it.
  • The steps are in GUIDE.md section 7 and skills/fire/contributing.md. Fire answers on the issue: adopted in a release, or declined with a reason.
  • npm run build:skill rebuilds the two lists; the build fails when they are stale.

Find the part by its job

Before you compose a screen, ask Fire what it already has. fire find searches components, patterns, templates, layouts and modules by what each is for, in the words an agent or a person would use. It reads contract/index.json. It needs no network.

Shell
npx fire find "approve a request"
npx fire find "date range with a comparison" --surface app --kind component
node node_modules/fire-design/scripts/find.mjs "show a status page" --json --limit 3
OptionDoes
--surface app|website|phone|emailKeeps parts made for that surface. A line says when a clearly better match belongs to another surface.
--data record|list|series|form|textKeeps parts that show that kind of data.
--kind component|pattern|section|template|moduleKeeps one kind. A section is one block of a website, a template is a whole screen. A layout counts as a component.
--limit 5How many results. The default is five.
--jsonPrints the entries for a script.
  • The index holds 233 entries, one per part: its job, other names, surfaces, data, when to use it and what to use instead. node scripts/build-index.mjs builds it from the cards; the build checks it is current.
  • A word counts more when few parts use it, and more again when it is in a part's name or other names. Words such as "approve" and "modal" also reach "decide" and "dialog".
  • Open the result's docs link and copy its markup. If nothing fits, follow GUIDE.md section 7.
  • Adding a part to Fire? node scripts/gate.mjs --probe <page> compares it with every template and fails a near-duplicate, unless its card declares a relation.
  • Each entry but a module has a picture at contract/pictures/<kind>/<id>.png. The index states that rule once, in its top-level pictures field, and fire find --json returns the resolved picture of each result. npm run build:pictures rebuilds them in a browser; the build only checks that none is missing. They are in the package from 0.13.0, with the reference screens and these docs pages, so an agent in a product can open them.
  • The Catalogue page shows the same index with filters and pictures. See Catalogue.
  • docs/_ref/CLASSES.md lists every class with its parts, attributes, values, state and events. node scripts/build-classes.mjs generates it from the catalogue, so it is complete.

Catalogue and cards

Fire describes itself in contract/catalog.json: 187 components, patterns, layouts and website sections (154, 10, 5 and 15), and 4 modules, with their classes, allowed values, states and events. Each has a card that says what it is for, when to use it, when not to, and what else people call it.

Card fieldUse it to
jobMatch a request. One sentence that starts with a verb.
akaMatch other names: "modal" finds the dialog.
surfaces, dataFilter: app, website, phone or email, a list or a record.
useWhen, avoidWhenConfirm the fit. Each avoidWhen names what to use instead.
exampleOpen the one docs section that shows it. Copy its markup.

How an agent searches

Search the cards by job and aka first. Filter by surfaces and data. Read useWhen and avoidWhen. Then open only the chosen entry's example.

Shell
node -e "
const c = require('fire-design/catalog');
const q = 'data grid';
for (const x of c.components) {
  const k = x.card;
  if (k && [k.job, ...k.aka].join(' ').toLowerCase().includes(q)) console.log(x.id, '-', k.job, '->', k.example);
}
"

That prints table - Compare, sort and act on records laid out in rows and columns. -> docs/data.html#activity. A class or attribute value that is not in the catalogue does not exist.

The checks

The three you run in a product are lint-markup, lint-css and render-equal. They run from the package and need Node; the last needs a browser too. The checks that keep Fire itself honest are in Fire's own checks.

lint-markup

Reads your markup and the catalogue. It reports unknown fd- classes, elements and icons, data-* values a component does not define, style attributes and props, raw colours and pixel sizes, icon-only buttons without a name, and <i data-icon> in React or Vue code. It exits 1 on any error.

Two findings are warnings, which never change the exit code. surface-mismatch reports a part whose card does not include the surface the page declares with data-fd-surface="app|website|phone|email" on <html> or any element; a phone page accepts app parts, and a page that declares nothing is not checked. --surface <name> sets the surface for files that declare none, and --no-surface turns the rule off. img-attrs reports an <img> inside fd-site without alt (alt="" is right for decoration) or without both width and height. The JSON output has a warnings count, and each finding a severity. See Catalogue.

Shell
node node_modules/fire-design/scripts/lint-markup.mjs "src/**/*.{html,tsx,jsx,vue,ts}"
npx fire lint src --surface app --json

Structure

From 0.10 the lint also checks how parts fit together, from facts on each card: which parts a component requires, which tag a class sits on, where a part may sit, which attributes it must not carry, and which native element a wrapper holds. Each fact comes from Fire's CSS or behaviour, and Fire's own docs, templates and starters pass every rule. docs/_ref/CLASSES.md shows the facts beside each class, and fire find prints a component's required structure as one line to write.

RuleReportsWrongRight
missing-partA part the component needs is absent.<div class="fd-callout"><div class="fd-callout-content">…</div></div><div class="fd-callout"><i class="fd-callout-icon" data-icon="info"></i><div class="fd-callout-content">…</div></div>
wrong-elementA class on a tag it does not work on, or on the native element it wraps.<select class="fd-select">…</select><label class="fd-select"><select>…</select></label>
wrong-parentA part outside the place it may sit, or inside a part that holds none of its kind (a text field in fd-setting-text).<div class="fd-grid"><section class="fd-form-section">…</section></div><form class="fd-form"><section class="fd-form-section">…</section></form>
forbidden-attributeAn attribute that breaks the part. missing-attribute is its pair, for one a part needs; no card asks for one yet.<div class="fd-menu" hidden>…</div><div class="fd-menu" popover role="menu">…</div>
missing-childA wrapper without the native element it styles.<label class="fd-switch"><span class="fd-switch-track"></span>…</label><label class="fd-switch"><input type="checkbox" role="switch"><span class="fd-switch-track"></span>…</label>

The lint sees source, not the page. It reports nothing it cannot see: a part is not missing where a hole, an expression, a slot or a child component sits where the part would go, and the parent of a template's or a component's top element is unknown, so a misplaced part there is found only on the rendered page, by fire review. No comment turns a rule off for one line or one file.

render-equal

Proves a screen renders like its reference: a Fire template or a design board. It compares Fire nodes, computed styles and pixels at 1440 and 375 wide, in light and dark, in Chromium, WebKit and Firefox. The framework's own markers are ignored, such as React's vt-* view-transition attributes (rule R14), and the pixel shot is of the root alone, so a fixed tab bar or a toast around the screen does not count (R15). Form state is compared through properties, so a field filled by a framework equals one written with value (R5). Each page loads under its own Content Security Policy (R13). The rules are in spec/EXPORT.md, and renderEqual.rules in spec/export-map.json lists every one it applies. It needs playwright-core, pixelmatch and pngjs.

Shell
node node_modules/fire-design/scripts/render-equal.mjs \
  --ref templates/logs.html --cand http://127.0.0.1:5173/logs \
  --ref-root ".fd-page" --cand-root ".fd-page"

All three run in each starter

Run npm run lint:markup and npm run lint:css in your project. Run npm run check inside Fire's repository, where the reference templates are: it builds the starter, compares its screens with the templates (the overview, logs and settings, and their empty, error and no-results views), visits every route, and runs both lints.

Review every screen

Lints read markup; they never see a screen. fire review opens every screen in a browser, at 1440 and 375 wide, light and dark, and every ?state= you list. It writes a gallery a person can look through in a minute and runs checks that need the rendered page. It exits 1 on an error; warnings never change the exit code. It needs playwright-core.

Shell
npx fire review --serve dist --spa --routes /overview,/logs,/settings
npx fire review --base http://127.0.0.1:3000 --routes routes.json --states --json
npx fire review                  # everything from package.json "fire": { "review" }

The configuration lives in package.json, so the command runs bare. A route is a path, or an object with a name, a state to open it at, the states that --states adds, and a setup: a cookie ("name=value", or an object with httpOnly, sameSite and the rest), keys for localStorage, or a selector to wait for. A __Host- or __Secure- session cookie works on http://localhost: the review sets it by domain and path, marked secure. A setup at the top applies to every route. Each screen is captured once it settles: fonts loaded, Fire’s elements defined, no loading marker left and the page quiet, up to a limit.

JSON
"fire": {
  "review": {
    "serve": "dist", "spa": true, "out": ".fire-review",
    "setup": { "storage": { "ember-whats-new-seen": "1" } },
    "routes": [
      { "path": "/logs", "name": "logs", "states": ["loading", "empty", "error"] },
      { "path": "/logs/req_7c19be", "name": "logs/:id" }
    ],
    "allow": ["a console message or URL you expect"]
  }
}

The gallery

.fire-review/index.html is a contact sheet: a count of screens, errors and warnings at the top, then one row per screen with its four captures side by side, each opening the full-page picture. Under a row, each finding gives its rule, its message, the widths and themes where it happens, the element as a short CSS path, the fix, and a cropped picture of the element. A row with an error has a red title. It is plain HTML with its own stylesheet, no script and no request outside the folder, so it opens from the file system. Look at every picture before a release.

overflow-xThe page scrolls sideways, or something that starts on screen runs past its edge and is cut off by the page. It names the widest offender, or the box its content spills from.
offscreen-controlA button, field or link button is cut by the edge of the viewport.
one-h1No rendered h1, or more than one. A visually hidden one counts; one in a closed dialog, or in a message’s rendered markdown, does not. A screen still showing a loading marker may lack one.
one-page-headMore than one page head (fd-page-head, fd-page-hero) in the main region, outside cards and overlays.
one-primaryMore than one primary button in one view: an open dialog, sheet or popover, a card, an empty state, a section of a public site, the main region, or the shell around it.
stretched-buttonA warning. At 900px and wider, a button with no data-block more than twice as wide as its label, stretched by a plain box or a layout part.

With scripts/lib/structure.mjs in the package, it also runs the catalogue’s structural rules on the rendered page, so markup a framework builds at run time is checked too; without it, it says so in one line. Every rule was measured on Fire’s own 42 templates, in every state their cards name, at both widths and in both themes.

What it cannot judge

  • Taste, hierarchy and rhythm: whether the screen reads well, or looks like a product rather than a database form.
  • Whether the screen follows the right template, or the right control was chosen for a value.
  • Keyboard use, focus order and the words on the screen. Use the screen, and run the checklist in WRITING.md.

In each starter, npm run check runs it as its last step and fails on an error. npm run review runs it alone: Lit and Vue build first; Next reviews a running npm start.

A slim build

fire slim reads your source and writes a Fire trimmed to what it uses: one stylesheet, one behaviour entry, the font files of your type set, and a report. The starters run it before every production build. In development you keep the whole of Fire, so nothing is missing while you write a screen.

Shell
npx fire slim src index.html --out .fire-slim --theme theme.json --level component --report
npx fire slim --check            # CI: fail when .fire-slim is stale for the sources
npx fire slim --verify dist      # fail when the build still holds a rule or a module the report dropped

With no sources it reads "fire": { "slim": { "sources", "out", "theme", "include", "level" } } from package.json. It reads what lint-markup reads: .html, .jsx, .tsx, .vue and html`…` templates, and every string in your code. The report, slim.json, names the file and line that kept each part, what was dropped, and the sizes before and after.

What it keeps

  • Every component whose fd- class, element (<fd-chart>, <FireChart>) or data-fd-* attribute appears in your source.
  • Every module whose export you import from fire-design: named, as a namespace, or with import().
  • What Fire builds at run time. A date field opens a popover with buttons, and the combined filter builds a menu and a sheet. The map of this is contract/slim-map.json, generated from Fire's own source.
  • Tokens, base and layout, and every rule that needs no Fire class. With --theme, only the record's palette and type set, and the fonts they use. A product that ships the Tweaks panel keeps every palette, type set and font.

--level family keeps whole stylesheets. --level component, which the starters use, also removes the rules inside them that can no longer match. The behaviour entry, fire.js, has the same exports and the same init() as Fire's, for the modules it keeps. Importing a dropped one fails the build by name.

Class names built at run time

No scan can read `fd-badge-${tone}` or className={cls}. --report lists each one with its file and line. Keep what they make with --include badge,charts,site, which takes components, modules and stylesheets by name.

Fire loaded by a path

A product that vendors Fire loads it by path: import { tweaks } from '/fire/fire.js', import('../fire/js/content.js'), or <script type="module" src="/fire/fire.js">. A specifier whose last segments are fire/fire.js is read like fire-design, and one ending fire/js/<name>.js keeps that module. A namespace used where no member can be read keeps every module, and slim.json says where. A script tag alone keeps nothing extra, the markup decides. loadedBy in the report says package, path or both. To use the output, replace the folder that path names with .fire-slim/, or alias it.

In the starters

The step that writes the theme stylesheet also runs fire slim with the same record: prepare.mjs in Lit, build-theme.mjs in Vue, prepare-fire.mjs in Next. In production, an alias points fire-design and fire-design/css at .fire-slim/: resolve.alias in vite.config.ts, turbopack.resolveAlias in next.config.ts. So does ../../fire/fire.js, which the React and Vue packages load, so the app has one Fire. The strict CSP and its nonce are unchanged. vite build --mode full or FIRE_SLIM=0 next build builds with the whole of Fire. Each starter's npm run check runs --verify and still compares every screen with Fire's templates.

The starters ship the Tweaks panel and the support chat, so they keep every palette, type set and font, and the chat, agent and tweaks modules. What it does not do

Your own CSS and tokens

Fire is constrained and open at the edge: a product may add its own tokens and its own CSS, under its own prefix. lint-css keeps that edge honest. It reads a product's stylesheets and the token contract, and it needs only Node.

The prefix rule

--fd- belongs to Fire. Your tokens go under a prefix of your own, such as --acme-. Say which one in package.json, or with --prefix (repeat it for more than one). A property that starts --_ is private to its rule and is never reported. A few --fd- names are component parameters (--fd-gap, --fd-cols, --fd-i, --fd-panel-w…), and you may set them.

JSON
{ "fire": { "prefix": "acme" } }

Run it

It checks .css files, <style> blocks in .html and .vue, and css`…` templates in .ts and .js (the static parts). It exits with 1 when there is an error. Warnings print and do not fail the run.

Shell
node node_modules/fire-design/scripts/lint-css.mjs src
npx fire lint-css src --prefix acme --json

What counts as a duplicate

A token of yours is a duplicate when its value, once resolved, is the value of a Fire token of the same kind. Colours compare by distance (#fff, white and rgb(255 255 255) are one colour, and so are two that differ by less than an eye can see), and lengths compare after unit conversion (0.5rem is 8px). The kind comes from the value, and for lengths from the name: radius, space, text size, line height, border width. Pure white and black are primitives and are not reported. Layout sizes (a sidebar width, a panel height) are not compared with Fire's size steps.

CSS
:root {
  --acme-radius: 8px;            /* duplicate-token: the same as --fd-radius-md, use it */
  --acme-ink: var(--fd-text);    /* duplicate-token: a second name for --fd-text, nothing more */
}

An alias is fine when it carries a role Fire lacks and is re-defined somewhere, per scope or per colour scheme. Then the name is the point, and each definition says something different.

CSS
:root { --acme-ink: var(--fd-text); }
[data-theme="dark"] { --acme-ink: var(--fd-text-2); }   /* re-defined: a role of its own */
RuleLevelWhat it reports
unknown-tokenErrorA var() of an --fd- name that is not in the contract. The message names the nearest tokens.
reserved-prefixErrorYou declare a custom property that starts --fd- and the contract does not list it. The prefix is Fire's.
token-overrideWarningYou set a scale or derived token. Setting an input token (a palette colour, a font, a dial) is what a theme record does, so it is not reported.
unprefixed-tokenWarningA custom property that is not --fd-*, not --_x and not under your prefix.
duplicate-tokenErrorA token of yours that repeats a Fire token, repeats another token of yours, or is a bare alias that is defined once on :root.
near-tokenWarningA colour or length of yours that is close to a Fire token and not equal: did you mean it?
no-raw-colorErrorA hex, rgb(), hsl(), oklch() or named colour in a declaration. A token definition is the one place for a colour value.
no-raw-sizeWarningpx or rem outside a token definition. 0, percentages, unitless numbers, calc() that multiplies a token, and @media conditions are fine. A 1px line is var(--fd-hairline).
no-raw-durationWarningms or s outside a token definition. Use the --fd-dur-* steps, so reduced motion and the motion dial apply.
no-fd-class-restyleWarningA rule whose subject is an fd- class and that sets more than where the part sits. Margin, grid-area, order, align-self, flex, position and a width through a token are fine. Ask for a variant, or style a class of your own.
no-importantWarning!important in a rule whose selector has an fd- class.

Fire's own CSS is not checked this way

The audit (node scripts/audit.mjs) covers Fire's stylesheets. Run npm run lint:css in each starter for the product side; npm run check runs it too.

Fire's own checks and commands

These run in Fire's repository. Most are in npm run check; the rest are npm run check:full.
