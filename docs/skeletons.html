Skeletons & loading

Loading keeps the layout. A skeleton has the exact geometry of the thing it stands in for, so the real content swaps in without a single line moving; a spinner is only for work too small or too unpredictable to sketch.

Spinners and text loaders

Use a ring inside controls and small panels, a braille frame or dots beside a sentence that says what is happening, and equaliser bars for a stream that is receiving data.

  • Give a lone spinner role="status" and an aria-label; a loader beside a sentence takes the sentence as its label.
  • .fd-braille gets its frame from JavaScript: write only the label. The frame cycles every 80ms and holds still under reduced motion.
  • Buttons do not take a spinner child: set aria-busy="true" on the button.

Skeleton parts

Line parts keep the full line height of the text they replace and draw a thinner bar inside it, so a title skeleton is exactly as tall as the title.

  • Title sizes follow the type roles: display h1 h2 h3, the default card title, lead label mono caption eyebrow stat.
  • Text lines vary their widths and end at 60%. Set --fd-i on a part to stagger its shimmer.

Card grid

For catalogs: tile, name and category, two lines of description and a foot. The grid uses the same tracks as .fd-grid.

  • Put fd-skeleton-card on an element that is also an fd-card and the card supplies the frame, so padding and border match by construction.

Table

Header bars are short and lighter, row bars vary by column, and the last column is right-aligned like figures.

  • Rows are --fd-row tall with a hairline, so compact density tightens them too. Under 480px only the first three columns remain.

Stat strip

Eyebrow, figure and caption per tile, separated by hairlines that wrap with the grid.

Chart

Axis ticks, gridlines and a faint breathing placeholder of the series, as a line or as bars.

List

Members, sessions or connected apps: avatar, two lines and a trailing action.

Agent thread

While a saved session loads: the user's message on the right, then the reply with a tool call between its paragraphs.

Form

Settings pages load their values: label, an empty field frame and the hint, then the actions.

Page hero and whole screen

The first paint of a route: rail, top bar, hero, toolbar and a table, built only from skeleton blocks.

  • Every screen is filled from an empty element by texture.js; write the parts by hand when you need a different arrangement and the same classes apply.
  • Below 640px the page drops its rail and secondary toolbar buttons, like the real shell.

Content swap

Wrap a skeleton and the real content in one container. While it loads, the skeleton sets the height; when it is ready the skeleton fades out and the content rises 8px into the same place.

Loading a page

A loading page keeps its frame and shows the shape of what is coming. There are three moments, and never a bare box of bars for a whole page.

  1. First load, before any script has run: fd-skeleton-app in the page's static HTML. It draws the app shell with the stylesheet alone, at the shell's own sizes, so the real shell lands on it without a jump. Remove it when the app mounts.
  2. Moving between pages: the shell stays and the page head shows its real title at once. Only the content region is a skeleton, the preset shaped like the screen: a table for a table, a list for a list, cards for a grid, a form for a form, stat tiles and text for a record.
  3. A section loading inside a page: the same, at the section's size.

the same skeleton in a 375px frame, with a phone tab bar

  • Write it with skeletonApp({ preset, nav, tabbar }) from fire-design/skeleton, or paste it. Under 900px the sidebar gives way to the top bar's brand tile; under 640px the tab bar shows when the app has one (fd-skeleton-app-tabbar). data-sidebar="collapsed" when the shell starts as a rail.
  • In a page it fills the screen: leave out data-contained, which is for previews like these.
  • Its inner preset is written filled, so it draws before any script: skeleton('table', { rows: 4 }) returns the same markup texture.js writes into an empty preset, with its widths in data-fd-vars. In static HTML, write presets filled. An empty fd-skeleton-text with data-lines (1 to 8) draws its lines with CSS until the script fills it.

Fast loads and slow loads

Inside a loading region a skeleton waits --fd-skeleton-delay (160ms) before it shows, so a fast load never flashes one; its space is held meanwhile. When a load takes longer than --fd-skeleton-late (6s), one muted line in your own words says so.

  • The wait applies inside data-fd-loading="true" and fd-states in its loading state, with reduced motion too (only the fade goes). Set --fd-skeleton-delay: 0s to turn it off, as the starters do for the first page after their first-load skeleton. fd-skeleton-app never waits.
  • fd-skeleton-late sits first in the loading region. It is hidden, with its space kept, until the time has passed; texture.js makes it a polite status and writes its words in at that moment, so a screen reader hears it once per load. When loading ends it goes, and the next load starts its own wait. This demo sets the time to about 3s.

Rules

Do

Sketch the real layout: the same number of columns, the same row height, a card per card. Keep the shell and the page head, and put the skeleton in the content region only.

Don't

Put a spinner in the middle of an empty page, stack a spinner on a skeleton, or keep a skeleton up after an error. Say what failed instead.

  • Skeletons are aria-hidden; the container's aria-busy tells assistive technology the region is loading.
  • Under reduced motion the shimmer stops and blocks sit at rest, at the same strength.
