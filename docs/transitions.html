Page transitions

Moving from one page to the next feels like one product: the chrome holds still and only the content changes. It uses the browser's View Transitions, so a browser without them navigates as it always did.

What moves

One region moves. Each part of the chrome has its own name, so it is never cross-faded. Names exist only under data-fd-transition.

NameElementDoes
fd-content.fd-main > .fd-page, .fd-doc-main, .fd-site main, a page of its ownMoves
fd-sidebar.fd-sidebarHolds still
fd-topbar.fd-topbarHolds still
fd-tabbar.fd-tabbarHolds still
fd-doc-top, fd-doc-nav.fd-doc-top, .fd-doc-navHold still
fd-site-header.fd-site-headerHolds still
fd-fab.fd-app-fabHolds still
  • The rest of the page is the root snapshot, which does not animate.
  • A specimen is never named: anything inside .fd-app[data-contained] or .doc-specimen keeps its own motion.
  • A name must be unique on a page. Two elements with one name make the browser skip the transition.

Three kinds

Choose with data-fd-transition on <html>. The default is fade.

ValueUse it forMotion
fadePages at one levelThe old page fades out in --fd-dur-3. The new page fades in and rises over --fd-dur-4.
slidePhone drill-downForward slides the new page in from the inline end. Back reverses it. Right-to-left pages mirror.
noneA page that must swap at onceNo transition.
  • One link can override the page: <a data-fd-transition="slide" href="https://ember.dev/logs">. It applies to that navigation only.
  • Direction comes from the browser's Navigation API: a move to an earlier history entry is back. data-fd-direction is on <html> while the transition runs.
  • Distances and durations are tokens: --fd-transition-out, -in, -rise, -slide, -slide-out. The motion dial scales them, and motion "none" makes them instant.

Between pages

A multi-page site opts in. A page that does not ask gets no names and no transition.

  • Link fire/transitions.css after fire.css. It is not part of fire.css.
  • Put data-fd-transition="fade" (or slide) on <html>.
  • Mark the module scripts that build the page blocking="render". Chromium drops the transition, with a console error, when a page paints before its scripts have run.
HTML
<html lang="en" data-fd-transition="fade">
  <link rel="stylesheet" href="fire/fire.css">
  <link rel="stylesheet" href="fire/transitions.css">
  <script type="module" src="fire/fire.js" blocking="render"></script>

In a single-page app

transition(update, options) runs a route change inside a view transition. It sets data-fd-transition while it runs and removes it after, so the page needs none.

TypeScript
import { transition } from 'fire-design';

// update may return a promise; the call resolves when the DOM is updated.
await transition(() => render(route), { kind: 'slide', direction: 'back' });
  • Without View Transitions, with reduced motion, or with motion "none", it calls update and nothing else.
  • With them, the browser calls update a frame later. The promise rejects when update does.
  • Vue: call it from a beforeResolve guard. Lit: wrap the route change. Next.js: wrap each screen in React's <ViewTransition> and set the attribute on <html>. The three starters do this.

Support and reduced motion

What a reader sees depends on the browser. Nothing breaks without support.

BrowserBetween pagestransition()
ChromiumVerified, with a render-blocking scriptVerified
FirefoxNot supported: pages load as usualThe browser has it; not verified here
Safari (WebKit)Not verifiedNot verified
  • With prefers-reduced-motion: reduce, fire/transitions.css opts no page in and transition() only calls update.
  • In WebKit's test build the incoming page did not paint during a transition, so the chrome may blink out in Safari. Treat Safari as unsupported until you have tried it.
  • The stylesheet and module need no inline style and no inline script, so a strict Content Security Policy is fine.
